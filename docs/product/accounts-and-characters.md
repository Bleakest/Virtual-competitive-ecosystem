# DISC-02 — Аккаунты и персонажи

**Дата:** 2026-11-08  
**Статус:** утверждено владельцем проекта 2026-11-08. Базовые правила взяты из DISC-01; дополнения DISC-02 приняты, явно обозначенные открытые вопросы оставлены на последующие задачи.  
**Задача:** [#3](https://github.com/Bleakest/Virtual-competitive-ecosystem/issues/3)

## 1. Цель и словарь статусов

Разделить **аккаунт** (учётные данные реального пользователя, авторизация) и **персонажа** (самостоятельная карьера внутри единого мира). Ни аккаунт, ни переключение персонажей не должны останавливать ход времени или матча.

- **Принято (DISC-01):** уже согласованная продуктовая константа; менять только через Decision Log.
- **Утверждено (DISC-02):** правило принято владельцем 2026-11-08; детализация и реализация возможны позже.
- **Открыто:** не блокирует описание сущностей, решается в профильной задаче.

## 2. Зафиксированные правила — принято

1. Один аккаунт может содержать **несколько независимых персонажей** (DEC-001).
2. Игровые роли ровно две: **PLAYER / игрок** и **MANAGER / менеджер** (DEC-012). Организатор не является пользовательской карьерой.
3. Роль задаётся при создании персонажа и **никогда не меняется** (DEC-003).
4. У роли собственная процедура создания и игровые действия (DEC-004).
5. Игрок выбирает **одну дисциплину**; карьера в другой дисциплине требует нового персонажа-игрока (DEC-005).
6. Менеджер способен работать с несколькими дисциплинами и не может одновременно быть спортсменом в рамках **того же персонажа** (DEC-006, DEC-007).
7. Все персонажи существуют в **одном непрерывном мире**, а матч проходит в реальном времени. Офлайн пользователя не останавливает мир (DEC-014–016).

## 3. Доменные сущности и связи — утверждено

```text
Account 1 ─── N Character
                 ├─ role = PLAYER  ─── 1 PlayerProfile ─── 1 Discipline
                 └─ role = MANAGER ─── 1 ManagerProfile
Character ─── 0..N CareerEvents
PlayerProfile ─── 0..N TeamMemberships (по времени)
ManagerProfile ─── 0..N ManagementAssignments (по времени)
```

| Сущность | Смысл и минимальные атрибуты |
|---|---|
| `Account` | `id`, атрибуты авторизации, `createdAt`, `status`. Не содержит навыков и игрового прогресса. |
| `Character` | `id`, `accountId`, `role` (неизменный enum), `displayName`, `status`, `createdAt`. |
| `PlayerProfile` | `characterId`, `disciplineId` (неизменный), состояние карьеры, навыки и статистика по правилам дисциплины. |
| `ManagerProfile` | `characterId`, состояние управленческой карьеры, достижения и репутация менеджера. Дисциплина не закрепляется за самим профилем. |
| `TeamMembership` | Принадлежность игрока команде во временном интервале; детали контрактов — DISC-06. |
| `ManagementAssignment` | Право менеджера управлять определённой командой во временном интервале; объём полномочий — DISC-06. |

**Инвариант:** каждый `Character` имеет **ровно один** профиль соответствующей роли; для `PLAYER` обязателен один `disciplineId`, а для `MANAGER` такого поля нет. Профили игроков и менеджеров не объединяются в одну таблицу с набором nullable-полей. Это концептуальная модель, **не выбор базы данных или ORM**.

NPC — отдельные участники мира; не подразумевается, что у каждого NPC есть пользовательский `Account` (DISC-04).

## 4. Создание и выбор персонажа — утверждено

1. Пользователь входит в **аккаунт**.
2. Видит список собственных персонажей и может создать нового.
3. Выбирает **PLAYER** или **MANAGER**. Для PLAYER обязательно выбирает поддерживаемую дисциплину. Для MANAGER дисциплина на этапе создания необязательна.
4. Указывает отображаемое имя; платформа валидирует его и одним действием создаёт персонажа и его профиль.
5. Пользователь выбирает **текущего персонажа** и попадает в соответствующий интерфейс.
6. При следующем входе может выбрать другого персонажа; ранее созданные карьеры сохраняются и продолжают существовать в мире.

Текущий персонаж — **контекст сессии/интерфейса**, а не смена идентичности аккаунта. Любой серверный запрос к игровому объекту должен проверять **владение персонажем**, его **роль** и **доменные полномочия**. Нельзя полагаться лишь на `characterId`, переданный клиентом. Сервер не принимает попытки сменить `role` или `PlayerProfile.disciplineId`.

## 5. Изоляция карьер и ограничения — утверждено

- **Отдельный прогресс:** навыки, репутация, командные назначения, достижения, рейтинги, статистика и потенциальные ресурсы относятся к персонажу / его профилю, а не ко всему аккаунту. Автоматических переводов между своими персонажами нет.
- **Независимость:** один персонаж не получает бонусов за достижения другого; один и тот же аккаунт может иметь игрока и менеджера в общем мире.
- **Участие в матче:** один персонаж не может занимать две несовместимые игровые позиции одновременно. Для первоначальной реализации принято **не более одного управляемого вживую участника от одного аккаунта в одном матче**. Остальные связанные персонажи участвуют только согласно будущим офлайн-правилам. Сервер проверяет это при регистрации/управлении, а не только в UI.
- **Смена текущего персонажа:** разрешена вне зависимости от расписания мира, но сама по себе не отменяет заявки, подготовку и уже идущие события.
- **Архивация:** вместо физического удаления персонажа, участвовавшего в матчах, сохраняем историю результатов и связи; точные правила удаления персональных данных проектируются отдельно.
- **Количество персонажей:** конкретный числовой лимит **не утверждён**. Решено сделать его конфигурируемым, а значение определить при формировании MVP (DISC-10). Не вшивать случайный лимит в доменную модель.
- **Защита от злоупотреблений:** запрет самопротивостояний и конфликтов интересов между персонажами одного владельца в одном турнире — **гипотеза**, подробные правила определить вместе с командами и матчами (DISC-06/07).

Не подтверждены торговля между персонажами, передача персонажа другому аккаунту, смена дисциплины игрока или объединение карьер; **не реализовывать** эти функции по умолчанию.

## 6. Минимальные тестируемые правила

- Аккаунт создаёт двух PLAYER в разных дисциплинах и MANAGER; у каждого независимый ID и прогресс.
- Смена персонажа не меняет роль и дисциплину уже созданных персонажей.
- Попытка создать PLAYER без дисциплины отклоняется; MANAGER без фиксированной дисциплины допустим.
- Пользователь А не может редактировать/отправлять игровые решения за персонажа пользователя Б.
- Смена аккаунтом активного интерфейсного персонажа не отменяет запланированный матч предыдущего.
- NPC и системные турниры не требуют создания пользовательской карьеры «организатор».
- Действия за двух собственных участников одного матча отклоняются, если нарушают ограничение одновременного контроля.
