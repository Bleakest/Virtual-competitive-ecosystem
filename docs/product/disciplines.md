# DISC-05 — Система дисциплин и расширяемость

**Дата:** 2026-11-08  
**Статус:** базовая продуктовая модель подготовлена; футбол и Counter-Strike изучены как **примеры**, выбор дисциплины MVP не сделан.  
**Задача:** [#7](https://github.com/Bleakest/Virtual-competitive-ecosystem/issues/7)

## 1. Цель

Обеспечить **единый соревновательный мир** с несколькими спортивными и киберспортивными дисциплинами, не превращая систему в набор несвязанных игр и не строя один «универсальный» алгоритм матча для всех.

**Принято ранее:** игрок создаётся в одной неизменной дисциплине; менеджер может работать в нескольких. Матчи симулируются платформой, без интеграции с настоящими игровыми серверами и без графического движка управления игроками. Футбол **11×11** и Counter-Strike **5×5** — исследовательские примеры, не подтверждённый набор MVP.

## 2. Общее ядро / различия

| Общее для всех дисциплин | Зависит от дисциплины |
|---|---|
| Аккаунт, персонажи, NPC, команды, назначения | Допустимый состав и игровые позиции |
| Календарь, соревнования, регистрация и допуск | Формат матча, фазы, способы победы |
| Реальное время и единое авторитетное состояние матча | Расчёт игровых эпизодов и итоговой статистики |
| Матч, участники, история событий, результат | Действия игрока, установки, тренерская тактика |
| Проверки прав, сроков и идемпотентность | Навыки, прогресс, показатели и баланс |
| Статусы событий и публикация результатов | Правила счёта, ничьи, овертаймы, карты/таймы |

**Базовое решение DISC-05:** у дисциплины есть стабильный `disciplineId` и **версионированный набор правил**. При создании/планировании матча фиксируется версия правил; дальнейшее обновление игры не переписывает старую историю и не меняет условия уже идущего матча.

## 3. Контракт дисциплины (концептуально)

```text
DisciplineDefinition
  id, name, category (SPORT | ESPORT)
  rulesetVersion
  rosterRules         // минимальный/максимальный состав, роли/позиции
  matchFormat         // этапы/таймы/раунды, счёт, завершение
  playerAttributes    // специфичные навыки и метрики
  actions             // разрешённые решения игроков / менеджеров
  simulationRules     // обработка игровых событий
  resultSchema        // результат + статистика по дисциплине
```

Это **контракт продукта**, не требование немедленно реализовать плагины, отдельные микросервисы или динамическую загрузку кода. Разумный первый шаг — явные модули правил внутри одного приложения. Общие сущности не должны содержать полей вроде `footballGoals` и `csHeadshots` одновременно.

Минимальные общие предметные данные: `Discipline`, `RulesetVersion`, `Team`, `Participant`, `Competition`, `ScheduledMatch`, `MatchEvent`, `MatchResult`. Поля статистики и действий принадлежат конкретному правилосету; в общих моделях хранятся типизированные ссылки и общие метаданные.

## 4. Пример №1: футбол 11×11

**Для исследования**, без обещания первого релиза:

- Две команды по **11 участников на поле**; в составе есть роли вратаря и полевых игроков. Заявка и замены требуют отдельных правил.
- Ход матча описывается футбольными фазами и эпизодами: владение, атака, удар, гол, нарушения; итоговый счёт — голы обеих команд.
- Предматчевые решения менеджера: состав, расстановка, тактический подход. Решения игрока: допустимые действия в отдельных футбольных эпизодах.
- Навыки могут включать точность, передачу, выносливость, защиту и специфичные вратарские характеристики. Это **кандидаты**, не утверждённая система прокачки.
- Статистика: голы, передачи, удары, сейвы и т.п.; конкретные формулы и полнота статистики — DISC-08.
- Не моделируем непосредственное управление движением футболиста. Приходящий в реальном времени пользователь выбирает события/решения, которые обрабатывает серверная симуляция.

**Открыто:** длительность симулируемого матча относительно реального времени, лимит замен, наличие ничьей, овертайм/пенальти, масштабы лиг, травмы и экономика.

## 5. Пример №2: Counter-Strike-подобная дисциплина 5×5

**Для исследования**, без подключения к серверам Counter-Strike:

- Две команды по **5 участников**; матч может состоять из раундов и карт; победитель определяется по правилам счёта раундов/карт.
- Система игровых эпизодов отличается от футбола: выбор позиции/подхода, экономические решения, столкновения, выполнение целей раунда.
- Менеджер задаёт состав и тактику/подготовку; игрок выбирает доступные решения в отдельных раундовых ситуациях.
- Характеристики могут включать реакцию, точность, командную работу и тактическую подготовку; это **предложения**, не финальные навыки.
- Статистика может включать победы по раундам, результативность участников и командные показатели.
- Фазы «подготовка к раунду → раунд → итог раунда» — пример дисциплинарного расчёта внутри **одного назначенного матча**, а не отдельный реальный сервер шутера.

**Открыто:** экономическая система раунда, карты, стороны, формат серий, длительность, баланс эпизодов, лицензирование/брендинг и итоговая дисциплина для MVP. Нельзя автоматически копировать все детали официальной игры без оценки реализуемости и прав.

## 6. Инварианты расширяемости

1. Создание нового типа дисциплины **не требует менять** модель `Account` или `Character`; PLAYER всегда привязан к конкретному `disciplineId`.
2. Менеджер допускается к командам разных дисциплин по отдельным назначениям и правам.
3. Участники команд и NPC проходят проверки, которые применяет **их** дисциплина, а не условный «универсальный размер команды».
4. Для каждого матча фиксируются `disciplineId` и `rulesetVersion`. Нельзя смешать участников несовместимых дисциплин.
5. Общий движок календаря управляет стартом и сохранением события, **специфичная симуляция** — правилами этого матча.
6. Результат хранит общие атрибуты (участники, победитель или ничья, статус) и специфичные данные (голы, раунды и т.д.).
7. Реальное время и серверная проверка действий едины; окна и типы решений могут отличаться по дисциплинам.
8. Расширяемость **не означает**, что в MVP обязаны быть две дисциплины: реализация одной дисциплины — допустимая проверка архитектурного контракта.

## 7. Минимальные проверяемые сценарии

- В мире зарегистрированы две дисциплины с **различными** правилами размера состава.
- Игрок одной дисциплины не может быть заявлен в матче другой, а менеджер имеет право назначаться в команды обеих (при наличии полномочий).
- NPC-игрок подчиняется тем же ограничениям дисциплины, что и игрок человека.
- Планировщик назначает матч; симуляция применяет **его** версию правил; результат сохраняется в общем формате плюс специфичные метрики.
- После обновления правил исторический матч продолжает ссылаться на предыдущую версию.
- Добавление третьей дисциплины не требует редактирования старых матчей или добавления специальных полей в `Account`.
